# Research 1: numbered captions, picture editor, photo studio (v1 spec to v2 port)

v1 = /Users/poojadudani/Documents/Claude cowork/Scholarly/appuscholer/index.html (cited as "v1 NNNN"). v2 = this worktree, apps/web ("web") and apps/api ("api"). Read-only research; no repo file changed.

## 0. Headline findings (read first)

1. **Document pictures in v2 are inline base64 data URIs inside the document's `bodyHtml`.** No blob store, no IndexedDB, no object storage, no `appuimg:` scheme. v1's `appuimg:` refs are dropped by the sanitizer on import (parity-deviations D-W0-5). Vercel Blob is mentioned only for PDFs in the v2 design (2026-10-13 design line 42/63); nothing in code uses it for document images.
2. **Save path**: Tiptap `editor.getHTML()` -> `Editor.tsx` `editor.on("update")` -> `useAutosave.onChange` (web/lib/useAutosave.ts, 1.5 s debounce) -> `createAutosaver.attempt` -> `seal()` -> `sealBody()` (useAutosave.ts:208) -> `apiFetch PUT /documents/:id`.
   - Vault OFF: `{bodyHtml: html, keyVersion: 0}`; api `resolveWrite` (api/src/routes/docWrite.ts) runs core `sanitizeHtml` + `wordCount`/`originCount` and stores the plaintext HTML, pictures included.
   - Vault ON: web runs `sanitizeHtml(html)` then `vault.encryptBody(doc, clean)` (AES-GCM under the document's DEK, output `iv.ciphertext` base64url, `keyVersion >= 1`) and sends `wordCount`+`originStats` computed client side. Api only checks the shape (`CIPHERTEXT` regex) and that the key version is known; it stores the blob untouched. **So pictures ARE encrypted with the vault on, because they are part of the one sealed string**; the server never sees them. A picture edit that goes back into the editor automatically takes this path. No second channel may carry picture bytes except same-origin BroadcastChannel between two windows (never to the server).
3. **Size ceiling**: api `DEFAULT_MAX_BODY_BYTES = 2.8 * 1024 * 1024` (api/src/app.ts:19), checked on the raw request string at documents.ts:28 (create) and :78 (PUT) -> HTTP 413 `too-large`. Ciphertext is 4/3 the HTML, so with the vault on the document HTML (all pictures + text) must stay under about 2.1 MB; base64 inflates image bytes another 4/3. **Web has no handling for a 413 on a document save**: `attempt()` catches it, sets status "error" (red "AUTO-SAVE OFF" badge, toast AUTOSAVE_STOPPED_TOAST) and retries forever at 2/4/8/16/30 s. Only the import path maps 413 (lib/import/run.ts:46). Every autosave also appends a full-body revision, so each picture edit stores the whole body again.
4. **v2 today drops `data-*` on paragraphs and images** (schema has no such attrs; chartStudio.ts:150 says "v1's data-cap attributes are not written: the editor drops them"). Caption marks (`data-cap`, `data-cap-title`, `data-cap-note`) and `data-edits` therefore need schema attributes. v1-imported `<p data-cap=...>` loses its mark on load today (stays plain bold "Figure 1" text).
5. **All 92 i18n keys for the three features already exist, identical to v1, in apps/web/messages/en.json and hi.json** (checked programmatically: 0 missing, 0 differing). Only `ps_size` is used in code (FormatBar font-size select). No new translation work unless new strings are invented.
6. Sanitizer facts (packages/core/src/sanitize.ts): tags include p, strong, em, span, img, table, figure, figcaption; attrs `href src alt title colspan rowspan class data-origin data-h data-run data-qcode style`; DOMPurify default ALLOW_DATA_ATTR is not turned off, so other `data-*` should pass, but the list does not name `data-cap*`/`data-edits`: **add a test that proves they survive `sanitizeHtml`** (and name them in ALLOWED_ATTR for clarity, as was done for data-run). `src` must match `^(https?:|mailto:|data:image/(png|jpe?g|gif|webp);base64,)`: a new picture must be PNG/JPEG/WebP/GIF base64; `data:image/svg+xml` and `appuimg:` are stripped.
7. CSP (web/proxy.ts) already allows `img-src 'self' blob: data:`; BroadcastChannel and `window.open` same-origin need nothing new.

## 6. Risks and unknowns
1. **Document size and the 413 loop** (finding 3): editing creates new full-size data URIs; four 1600 px photos can pass 2.1 MB. Unknown product decision: surface "this document is too large to save" before inserting/applying (budget check on `editor.getHTML().length` vs ~2.1e6 with vault, ~2.8e6 without), and/or lower `MAX_IMAGE_SIDE`/quality. Also v2 `resizeImage` returns PNG for any non-JPEG (screenshots can be several MB); v1 fell back to JPEG above 400k chars. Port that fallback in the same change or large PNG edits will break saving.
2. Revisions store whole bodies per save: heavy for picture documents (api store); out of scope but worth telling OJ.
3. Sanitizer: unverified in this repo that `data-cap`, `data-cap-title`, `data-cap-note`, `data-edits` survive `sanitizeHtml` in both web (vault path) and api (plaintext path); first test to write. The editor's `ClassSpan` also keeps `data-*` on spans, unrelated.
4. Renumbering model (explicit-only vs automatic) is a product decision; v1's help text says automatic, v1 code is explicit. Automatic renumber changes the document without the student typing, which also feeds the "My writing" origin counts (origin is by span classes, so plain text edits to a bold "Figure n" should count as the student's own; confirm `originCount` does not treat them as typed words; low risk).
5. Studio position tracking: image position can shift while the studio is open (the student keeps typing); re-find by `src` is a heuristic and fails if two identical pictures exist. Safer: stamp a transient unique `data-psid` attribute is NOT recommended (it would persist into saved HTML); instead remember pos+src and map pos through `tr.mapping` using a ProseMirror plugin state or `editor.on("transaction")`.
6. Studio window with a locked vault or signed-out session: the `(app)` layout redirects to /signin when the cookie is missing; the studio's picture lives only in memory/channel. If the opener closes, `ps_noparent` shows and "Save a copy" is the only way out.
7. Popup blockers and mobile browsers that open tabs: fallback to the dialog editor is part of v1; keep it.
8. Plaintext copies of private (participant) pictures: the channel message and the studio's canvas hold unencrypted bytes in browser memory; that is inherent in v1 and acceptable, but never write them to localStorage/IndexedDB/query strings (id only in the hash). Stating this in the dialog is optional.
9. Pixelate faithfulness: v1 relies on the browser's default downscale filter; exact bytes differ across browsers, so tests assert geometry (block size, sw/sh) and e2e checks that pixels in the box changed, not exact colours.
10. Accessibility: drag-only tools have no keyboard route (v1 too). Decide scope (numeric rectangle inputs) before building.
11. Out-of-scope but adjacent: Word/LaTeX export of figures (latex.ts: "images are not exported"); Word export keeps HTML as is.
