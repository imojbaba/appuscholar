# Fix Wave A (bugs and data fixes before the redesign) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The live stage 2 build stops losing or garbling data (authors, volume, issue, pages, citing papers, titles, limitations, the paper being analysed, concurrent saves, the export) and shows its real build number, with v1's tools doing what they did and every difference in the register.

**Architecture:** v1 port functions stay verbatim with their golden tests; each fix is a named v2 sibling beside the port (`…V2`), or, for parse fields that are only added, an in-place change whose golden test compares the v1 view. One storage change (a `version` column on `project_blobs`) gives blob saves an optimistic check; the browser re-reads and replays its own edits on a conflict. The account zip gains every stage blob, decrypted in the browser.

**Tech Stack:** TypeScript, pnpm/turbo, Next.js 16 / React 19, Hono on Vercel, Drizzle on Neon Postgres, WebCrypto vault, vitest, Playwright, the golden harness in `packages/core/test/harness`.

**Spec:** `appuscholar-blueprint/notes/2026-10-20-stage2-live-walk.md` (the 29 faults), `appuscholar-blueprint/design/2026-10-20-impact-map.md` (file:line evidence, §5 order constraints, §6 omissions 1 and 2), `appuscholar-blueprint/design/2026-10-20-journey-redesign-draft.md` §10, §12 and §13 (what this wave is and is not). Register: `docs/superpowers/specs/parity-deviations.md`. House style: `docs/superpowers/plans/2026-10-19-stage2-idea-literature-screens.md`.

- Schema: `project_blobs.version integer not null default 0`. SQL: `ALTER TABLE "project_blobs" ADD COLUMN "version" integer DEFAULT 0 NOT NULL;`
- Types: `ProjectBlob` gains `version: number`; `BlobWrite` gains `expectedVersion?: number`; `export class VersionConflictError extends Error { constructor(public current: number) }`.
- Store: every write that changes a body sets `version = old + 1` (insert → 1; `rewriteBlob` too, and still leaves `updatedAt`). `expectedVersion` undefined: today's upsert. `expectedVersion` 0: create, or update a row whose version is 0; otherwise `VersionConflictError(current)`. `expectedVersion` > 0: update only where `version = expectedVersion` (never insert); a missing row is `VersionConflictError(0)`. The compare and the write are one statement (`setWhere`), and a row-less result is told apart from `DekExistsError` by re-reading the version.
- Wire: GET and PUT answer `{ kind, body, keyVersion, deks, updatedAt, version }`; GET also sets `ETag: "<version>"`.
- PUT reads `If-Match` (`^"?(\d+)"?$`; anything else is 400 `invalid`); a conflict is 409 `{ error: "version-conflict", version: <current> }`. No header: as today.
- CORS `allowHeaders: ["authorization", "content-type", "if-match"]`.

### Task 5: The browser re-reads and replays its edits on a conflict

**Files:**

- Test: `apps/web/test/useProjectBlob.test.tsx`

**Interfaces:**
- Consumes: Task 4's wire and 409.
- `BlobWire` gains `version?: number` (absent from an API older than Task 4).
- `ClientDeps.put(body: BlobPut, ifMatch?: number): Promise<BlobWire>`; the hook sends header `if-match: "<n>"` only when `ifMatch` is a number.
- `ClientDeps.onConflict?: () => void`; the hook toasts `t("blob_conflict")`.
- The client keeps `version: number | undefined` (a 404 read is 0; set from every read and save) and `sinceBase: HeldOp<T>[]`, the sets made since the last value read from or accepted by the server (a successful save keeps only the sets made after its value was taken).
- On `ApiError` 409 `version-conflict`: read again (no passphrase prompt beyond the existing rules), `value = applyOps(sinceBase, fresh)`, save with the new version; up to 3 attempts. After the third conflict the value is held, `error` is true and `onConflict` is called once. A locked re-read holds the value as today.
- `blob_conflict` en: "This was changed in another window at the same time, so your change is not saved yet. It is kept here and saved with your next edit."
