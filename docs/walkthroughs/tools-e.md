# Tools E walk-through: Review's Closeness, Make PPT and Viva

Definition of done for session E of the stages 3 to 6 tools plan (`docs/superpowers/plans/2026-10-21-stages-3-6-tools.md`): the three tabs of the Review place are built. **Closeness** compares the document with the papers on the Reading shelf, the project's other documents and a pasted passage, in a Web Worker. **Make PPT** turns the document's headings into a .pptx deck. **Viva** (and the toolbar's **Viva question** button) asks one AI question about the selected text and keeps the student's own answers. A student meets each of them on the live site. Tests passing is necessary, not sufficient.
Walked by OJ, in Chrome, on the live site. A part of this runs automatically in `apps/web/e2e/tools-e.spec.ts` (in development mode, with the AI answered from a recorded reply, never a real AI call); the column "e2e" says which rows it repeats. Everything in the section "UNVERIFIED" is covered by this sheet alone. Keep the two in step.

**Site:** https://appuscholar-web.vercel.app
**You need:**
- **An account with a project** whose idea is saved (the walk account from wave B1 will do), signed in. Use the project's passphrase if the vault is on.
- **Your Groq or OpenAI key** set up (rows 14 to 17 ask the AI one question each; the AI sees the text you selected, after the personal-data check).
- **A desktop browser** at about 1440 px wide, Chrome, with the browser's downloads folder easy to open.
- **PowerPoint, Keynote or Google Slides** to open the downloaded deck (row 10).
- **For row 5 (the big check):** a long text and 20 papers. The long text: open Terminal on a Mac and run `sort -R /usr/share/dict/words | head -50000 | tr '\n' ' ' | pbcopy`. That puts about 50,000 different words on the clipboard (nonsense order, which is fine). Then paste it in the document with Cmd+V. For the matches, also copy one real paragraph (at least 40 words) from one of your papers and paste it somewhere in the middle of that text. The papers: put 20 PDFs on the Reading shelf (any open-access papers, from the Research tab or your own), or as many as you have and write the number in the row's result.

**Record:** fill the last column for each row with `VERIFIED` or `FAILED` and the date (`YYYY-MM-DD`); a row that cannot be done on the day is `UNVERIFIED`, with the reason. Anything FAILED is fixed and re-run before session E is called done. Build under test: open **Help** in the header and read the "Version ..." line at its top; write it here: `________`

## UNVERIFIED by the session that built these tabs (the walk must cover them)

- **Production build.** The e2e ran against `next dev`. A production `next build` compiled in the earlier tasks, but the PptxGenJS bundle, the Closeness Worker chunk and the page's policy for scripts in production were never run in a browser. Rows 2, 5, 8 and 10 on the live site are the first real check. (The policy's `worker-src 'self' blob:` is the same in development and production; only `script-src` differs.)
- **The big check (row 5).** 50,000 words against 20 papers in a Worker, with typing staying free, was measured only on the engine in Node (about 250 ms), never in a browser.
- **The deck in PowerPoint, Keynote and Google Slides (row 10).** The e2e unzips the file and reads its XML; it does not open it.
- **The selection staying through the move to Review (row 11).** It holds in the e2e (the prompt carries the selected paragraph); on the live site it depends on the editor staying mounted, so the walk repeats it. If it ever fails, the fix is to capture the selection when the button is pressed.
- **A locked vault (row 19)**, **Hindi (row 18)**, **the AI-use log (row 17)**, **the 61-answer limit (row 16)**, **settings per project (row 6)**, **other documents as sources (row 7)** and **dragging a question (row 14)** have unit tests but no browser run.
- **Layout.** Narrow screens (375 px), the dark theme and keyboard-only use of the three tabs were not looked at.
- **Typing while a long check runs** is in no automated test.
